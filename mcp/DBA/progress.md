# DBA MCP server: progress (Dasha - Bhukti - Antara and everything around timing)

for Vimshottari first and then every other dasha family, plus the things that make a dasha reading usable: lord facts, sandhi,
transit overlay (gochara / double transit), multi-dasha convergence, event-window search, rectification, and a **validation harness**
that measures how specific and how accurate any rule really is.

## Design rules (carry over from the project + new ones)
1. **Facts, not predictions.** Every result carries `rule_id`, `school`, `source`, `options_used`, and (where time is involved) an `uncertainty` block.
2. **Every school-dependent rule is an explicit option**, default = the mainstream convention, and the output says which one ran.
3. **Windows, not dates.** Results are intervals with a `coverage` number (share of the searched range that the rule marks) so the caller can see how specific the rule is.
4. **Resolution awareness.** Birth-time error, ayanamsa choice and year-length convention move boundaries; sub-levels shorter than that shift are flagged `below_resolution`.
5. **Independent evidence only counts once.** Dasha systems computed from the same Moon/lagna are not independent; convergence output says so.
6. Pure date math is exact (integer seconds or `Fraction`), no float drift; astronomy comes from Swiss Ephemeris (`pyswisseph`, already in `.venv`) or the `mcp/dasha` engine for exotic systems.
7. Project rules: install NOTHING (only edit `requirements.txt`); never print secrets; run with `.venv/bin/python`; long jobs through `start_process` + log polling; no `__init__.py` in `mcp/`; avoid recursive grep on the project; run scripts, not `python -m`.

### H. Validation and measurement harness (priority 1; this is the accuracy part)
32. **Case store and schema**: birth (with an accuracy grade, e.g. Rodden-style AA/A/B/C), events (type, date, date precision day/month/year, source). Import from CSV/JSON the user supplies; do not scrape.
33. **Pre-registration**: freeze rule ids + options + year convention + ayanamsa into a hash BEFORE scoring; split cases into tune and held-out sets; refuse to report held-out numbers for a rule set that was edited after looking at them.
34. **Metrics** `dba_backtest(rule_set, cases)`: hit rate, **coverage** (share of timeline flagged), **lift = hit rate / coverage**, window length, Brier and log score when a rule is converted to a probability (P(event in window | rule) against the base rate), calibration table, bootstrap confidence intervals.
35. **Baselines and controls**: random windows of equal length and equal coverage; age-based base-rate model (reference class, e.g. age at first marriage) as the outside view; chart-shuffle control (apply person A's rule set to person B's events); permutation p-values; multiple-comparison correction (Bonferroni / Benjamini-Hochberg) across rules x events x systems tried.
36. **Stacking guard.** Adding techniques widens what counts as a hit; one amateur study of 597 marriages reports a rise from 25% to 79% as six techniques are stacked, with no chance control (R12). The harness must report the chance-level hit rate for every stacked criterion and the incremental lift of each added technique.
37. **Chart-matching test (Carlson style)**: N charts vs N event histories, shuffled; can the rule set pair them better than chance (top-k accuracy)? Double-blind by construction (scoring code never sees the true pairing).
38. **Uncertainty bands** on every window: propagate birth-time sigma, ayanamsa set and year-length convention into start/end dates (item A.4).
39. **Reference-class base rates**: per event type, age distributions from whatever data the user supplies (no bundled stats unless a vetted public table is found); shown beside any chart-based window so the outside view is always present.

## Research notes (round 1, 2026-11-20)
Source quality legend: **P** primary/classical or recognised author; **S** secondary article; **M** marketing/SEO page (used only for conventions, never as evidence of accuracy).

### R1. Vimshottari structure and formulas
- 120-year cycle, nine lords, fixed order (Ketu, Venus, Sun, Moon, Mars, Rahu, Jupiter, Saturn, Mercury); each three nakshatras per lord; the Moon's nakshatra at birth fixes the first Mahadasha and the fraction elapsed fixes the balance (S, M: Wikipedia, hindutone, dekhopanchang, roxyapi).
- Antardasha length = Maha years x Antar years / 120; the first Antardasha is the Mahadasha lord's own; the same order continues. Finer levels repeat the proportion (S).
- Wikipedia (citing Rele): the balance is found by the rule of three only for the first Mahadasha; later ones run in full. Parashara names many systems; Rele says only Vimshottari and Ashtottari are in vogue (S).
- Practical precision ladder in one source: Maha (years) -> Antar (months) -> Pratyantar (weeks) -> Sookshma (days) -> Prana (hours); for most practical use Maha + Antar is called sufficient (M).

### R2. Year length (the biggest silent source of date differences)
- BPHS prescribes the 120-year cycle but is silent on the length of a "year" (S: dekhopanchang methodology page). Three conventions in practice: 365.25-day Julian year (mainstream), 360-day savana year (small minority), others (365.2425, tropical 365.2422).
- JHora, Parashara's Light, KP software and most published tables use 365.25 (S/M). **CORRECTION (verified by running code and reading source 2026-11-20, see V1): the installed PyJHora 5.0.0 does NOT use 365.25; by default it uses the true tropical (Sun-return) year, which averages about 365.2425 days/year, and fixed modes are optional. Treat the "JHora uses 365.25" claim as false for this install.** A scholarly article (Shyamasundara Dasa) argues for the solar 365.25 on classical grounds and says the 360 idea comes from confusing tithi counts with solar days (S).
- Size of the effect (own arithmetic, consistent with a developer guide): 18 x 365.25 = 6574.5 days vs 18 x 360 = 6480 (94.5 days for a Rahu Mahadasha); Venus 20 years = 105 days; Saturn 19 years = about 100 days; a whole 120-year cycle differs by 630 days. The ratio 1.0146 is close to 1, so a single-chart check can hide the bug: test two epochs a decade apart (M developer guide, own computation).
- Rule of thumb from that guide: a discrepancy under 2 days between tools is Moon-longitude rounding; 50-100 days points to the 360 convention; an hour-to-day shift only in pre-dawn births points to a time-zone/UTC date bug.

### R3. Sensitivity to birth time and ayanamsa
- Moon averages about 13.2 deg/day (about 33 arcminutes/hour; real speed 11.8-15.4); one nakshatra = 800'. A 15-minute error moves the whole timeline by: Venus 75.3 days, Saturn 71.6, Rahu 67.8, Mercury 64.0, Jupiter 60.3, Moon 37.7, Mars/Ketu 26.4, Sun 22.6 (S: one calculator article; I re-derived the Venus figure: 8.25' / 800' x 20 x 365.25 = 75.3 days). One hour of error is about ten months for a Venus-ruled birth star in another source.
- If the Moon sits near the end of a nakshatra, a small error can change the first Mahadasha lord itself; a Moon near a boundary is the fragile case.
- Lagna moves about 1 deg per 4 minutes on average; lagna, cusps and divisional lagnas change within minutes (relevant for house-based facts, not for the Moon-based dasha clock).
- Ayanamsa effect (own arithmetic from the probe table in `mcp/kp/progress.md`): Lahiri minus Raman is about 1 deg 27' at J2000, which is 10.9% of a nakshatra; for a Venus-ruled Moon star that is about 2.2 years of Mahadasha shift. Lahiri minus KP-old is about 5'49" (0.73% of a nakshatra, about 53 days for Venus). So ayanamsa choice can matter more than a quarter-hour of birth time.

### R4. Classical corpus
- BPHS (via Santhanam's translation) lists about 32 dasha systems; adding Varnada and Sudarshana Chakra gives 34; other counts are 42 (Rele) and "at least 43" (Wikipedia). BPHS names the nakshatra-based conditional dashas (Ashtottari, Shodashottari, Dwadashottari, Panchottari, Shatabdika, Chaturashiti-sama, Dwisaptati-sama, Shashtihayani, Shattrimsha-sama), the rasi dashas (Chara, Sthira, Kendra, Karaka, Brahma-grahashrita, Mandooka, Shoola, Yogardha, Drig, Trikona, Rasi, Panchaswara), and others (Yogini, Pinda, Naisargika, Ashtakavarga, Sandhya, Pachaka, Tara). The text itself says not all are appropriate (P/S).
- Mantreswara's Phaladeepika (dasha chapter; Ashtakavarga chapter) and Vaidyanatha's work are cited for combining Ashtakavarga with dasha (M/S, verify against the texts before coding).

### R5. Conditional dashas: applicability
- Different conditional nakshatra dashas apply to 8.33%-50% of charts; several overlap; PVR Narasimha Rao argues Parashara's conditions are necessary but not sufficient (Vimshottari may still dominate when a condition is met) (S, scholarly).
- Disputes recorded: Ashtottari (Rahu kendra/trikona from lagna lord; Ardradi vs Krittikadi variants; Mansagari's paksha rule); Panchottari (Cancer dwadashamsa only, or Cancer lagna as well); Dwadashottari (Venus navamsa vs vargottama); Shodashottari and Shat-trimsha-sama use Sun/Moon hora with paksha or day/night, and one practitioner site notes at least one of these two always applies.
- K.N. Rao and V.P. Goel wrote dedicated books on Shodashottari, Shashtihayani and Yogini (P-ish; commercial pages), claiming wide applicability; no controlled evidence seen.

### R6. Rasi dashas, Kalachakra, Yogini
- **Chara**: begins at the lagna sign; direction groups (direct/reverse) differ by school; Scorpio (Mars + Ketu) and Aquarius (Saturn + Rahu) dual-lord handling differs by school; period of a sign = distance to its lord (count-minus-one convention in K.N. Rao's reading); K.N. Rao's version follows the Neelakantha method (no padakrama order); Raghava Bhatta and Nrisimha Suri give different calculations; the total is not fixed (about 144 years is only a convention). Raghava Bhatta does not use dual lordship for the dasha but does for the 8th house in longevity (S, forum/blog/PVR articles).
- **Narayana** (Sanjay Rath): sign dasha with odd/even-footed sign rules; used with Ashtakavarga (SAV and BAV) and a Panchakadi relation scheme; paired in that school with Vimshottari (S).
- **Kalachakra**: four groups of nakshatras, savya/apasavya direction, four padas, sign sequences with paramayus figures (100/85...), Deha and Jiva signs; Sumeet Chugh says the "first dasha fraction" starting method does not work well; PVR says afflictions to Deha/Jiva signs in rasi or D27 can indicate health dangers (S).
- **Yogini**: 36-year cycle repeating several times in a life; K.N. Rao suggests varied starting points for later cycles (lagna, Sun, next nakshatra) as a progression idea (S).
- Combination: one source sets Vimshottari, Kalachakra and Yogini at weight 1/3 each; Rath advises at least three timing methods together (S).

### R7. How dasha results are read (interpretation inputs the dossier must expose)
- Common thread across sources: the promise comes from the natal chart (placement, strength, aspects, lordship, varga support); the dasha activates it in time.
- Mahadasha lord factors: natural significations, houses owned, house occupied (the "single most important factor" in one popular source), aspects/conjunctions, dignity, Shadbala, navamsa/pushkara status, benefic/malefic for the lagna.
- Antardasha: the sub lord's own condition, its relationship to the Maha lord (friend/neutral/enemy), houses counted from lagna and from the Maha lord (classical dasha-phala principle), yogas the pair forms.
- A source on malefic house lords (3, 6, 11) says their harsh results show in the sub-periods of planets connected to them rather than their own (S, partial text; verify before coding).
- Yogas (e.g. dhana yoga) are assessed through the Maha/Antara periods of the participating planets.
- Several teachers warn that one dasha system alone can mislead and that general planet labels ("Saturn periods are bad") are not reliable.

### R8. Dasha with transit
- Double transit (Jupiter + Saturn both on the target house/lord by occupation or aspect): attributed to B.V. Raman, widely quoted from K.N. Rao ("Jupiter and Saturn in transit play a pivotal role"); framing: dasha supplies the promise, double transit supplies the window; applied from lagna and Moon. A worked source notes the overlap house shifts roughly yearly and only a couple of Jupiter-Saturn configurations have no overlap (S).
- Faster planets (Moon, Mercury, Venus) are called too quick for major-event timing but are used as fine triggers; Venus transit over the 7th cusp for marriage is one example (M).
- Ashtakavarga conventions seen (M): dasha lord's BAV in its sign >= 4 favourable; SAV 28+ strong, under 25 weak; Rahu dasha uses Saturn's BAV, Ketu dasha Mars's; Kakshya for closer timing; Phaladeepika ch. 18 cited. Treat every threshold as an option with its source.
- Sudarshana Chakra: three charts (lagna, Moon, Sun) advance together; recommended as an extra layer beside Vimshottari and gochara.

### R9. Dasha sandhi
- Sandhi = changeover zone between two Mahadashas (and between long bhuktis). Neither outgoing nor incoming lord is said to perform at full strength during it. Three conventions found: about six months either side (M), 10% of each Mahadasha length (M, with friend/neutral/enemy intensity labels), and per-pair figures such as about 9 months around Sun->Moon (S, Barbara Pijan Raden). No source gives evidence; keep as options and report only dates and lord-pair relation.

### R10. Rectification with dasha
- Event matching against dasha/antardasha boundaries, divisional charts, KP ruling planets, and transit-to-angles (outer planets crossing the angles; angles move about 1 deg per 4 minutes) are the methods named. Rule of thumb: round times are treated as centres of +-15 to 30 minute windows; rectification is elimination of candidates that contradict dated events and cannot create a time from nothing.
- Practice advice found: treat a chart with a known time as unknown and try to recover it (becomes item G.30).
- Moon-based dasha clock is robust unless the Moon is near a nakshatra boundary; lagna-based facts are the fragile ones.

### R11. Longevity / maraka caution
- Classical material lists maraka periods (2nd and 7th lords), badhaka, 8th house, Ayurdaya methods and Shoola dashas. Reputable-practitioner statements found say a single period is never used to predict death; convergence of several factors is required and the discussion is about longevity, not dates (M). Jaimini approach: three pairs (Sun, Moon, lagna based) each indicating long/medium/short life; three long pairs give 108 years (S, Rath answer text).

### R12. Evidence and validation pitfalls (why item H exists)
- **Controlled tests of astrology**: Carlson's double-blind test (Nature 1985) found astrologers could not match natal charts to personality profiles above chance; Dean and Kelly's meta-analysis surveyed more than 40 controlled studies with about 500 astrologers with weak results; Ertel re-analysed Carlson and argued the negative verdict was too strong but, on his own account, the data do not verify astrology (S). These tests concern personality matching, not dasha timing.
- **Dasha-specific evidence**: none found that is controlled. The Pune double-blind test of Indian astrology (about 12 years ago) and a skeptic re-analysis of its data for predictive houses found no signal (S, skeptic site). A KP-community study of Mars dosha on about 100 marriage charts found no strong correlation. A marriage-timing book claims a very high hit rate from a "statistical replicable research" without published controls (M).
- **Stacking pitfall**: an amateur study of 597 marriages (Davison charts) reports 25% (transit only) rising to 79% as six techniques are stacked; adding techniques widens what counts as a hit, and without a shuffled-chart control the numbers say nothing about skill. Directly motivates items H.35-H.36.
- **Windows vs dates**: popular sources themselves frame dasha timing as windows (e.g. a 19-month window), which makes coverage (share of life marked) the key specificity number.
- **What does improve accuracy in any forecasting field** (from prior research round): outside view / base rates first, probabilities scored with Brier or log score, decomposition and incremental updating, aggregation of diverse forecasts, held-out evaluation. Item H applies exactly these to dasha rules.
- Back-of-envelope for coverage (not a source): if a rule needs the Maha lord in a set of k planets AND the Antar lord in the same set, the time share is roughly the product of the two time-weighted shares (for k = 3 of 9 about 11%); if either lord qualifies it is roughly 1 minus the product of the complements (about 56% for k = 3). Compute exactly in the engine from real period lengths; do not trust this estimate.
